# PPTX engine decision (phase 5, item 4)

Evaluated `pptxviewjs@1.1.9` and `pptx-browser@4.1.5` against the 2-slide
fixture deck in `tests/fixtures/sample.pptx` (generated by
`tests/fixtures/generate-pptx.mjs`).

## Result

**Winner: `pptx-browser`.** The wrapper in `./pptx.ts` targets it.

## Evidence

- `pptx-browser` imports cleanly, loads the fixture, and reports
  `slideCount = 2`. Rendering is verified in the browser by
  `tests/pptx-engine.e2e.ts` through the `src/routes/engines/pptx/` harness.
- `pptxviewjs` cannot be imported at all in this repo: its published ES
  bundle (`dist/PptxViewJS.es.js`) has a static
  `import ChartModule from 'chart.js/auto'`, but `chart.js` is not installed
  (its `peerDependencies` mark it optional, yet the bundle imports it
  unconditionally). Node fails with
  `ERR_MODULE_NOT_FOUND: Cannot find package 'chart.js'`; a Vite build
  would fail the same way. It was therefore never able to load the fixture.

## Supporting reasons

- Zero dependencies (`DecompressionStream` + `DOMParser` + Canvas 2D) vs. a
  ~46k-line bundle with optional-but-actually-required peers. Smaller,
  auditable, and no CDN fallback code paths (`pptxviewjs` falls back to
  loading jszip from cdnjs at runtime).
- ESM-first with `sideEffects: false`, so the dynamic `import()` in
  `loadDeck` tree-shakes and stays client-only.
- API parity for what the viewer needs: `load()` → `slideCount` →
  `renderSlide(index, canvas, width)` → `destroy()`.
- Cost: `pptx-browser` ships no TypeScript types, covered by the minimal
  `declare module` shim in `./pptx-browser.d.ts`.

## Not done here

Removing the `pptxviewjs` dependency is intentionally left to the parent
task.
